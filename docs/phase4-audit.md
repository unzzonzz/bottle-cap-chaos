# PHASE 4 — 화면 정보 감사표 (지시서 v3)

승인 게이트 산출물. 구현(PHASE 5·6)은 이 표가 승인된 뒤에 시작한다.

> v2 의 같은 감사는 `docs/phase5-audit.md` 에 있고 **폐기가 아니라 역사**다.
> 그때의 기준은 "적게, 크게" 였고 지금 §11 은 그 역이다. 같은 요소에 대해 두
> 문서가 반대 판정을 내리는 곳이 있으면 이 문서가 이긴다.

## 이 감사의 자

§11 의 다섯 줄이 전부다.

> 큰 게이머 HUD · 두꺼운 패널 · 배지 · 광택 컨트롤 · 큰 버튼 · 모바일 게임 카드 — **금지**
> 작은 타이포 · 얇은 선 · 미세한 기호 · 최소 정보 · 정밀한 여백 — **사용**
> **필드가 화면을 지배한다. UI 는 주변에 조용히 앉는다.**

그리고 §14 의 침해 불가 목록 — 이 감사가 **무엇도 제거할 수 없는** 여덟 항목:

1. 1P/2P 뚜껑이 색과 명도 양쪽으로 구분된다
2. 아웃 라인 / 보드 경계가 보인다
3. 오차 콘이 배경 위에서 읽힌다
4. 컬링 거리 마크가 읽힌다
5. 카드 사용 가능 / 불가 / 침묵이 구분된다
6. 축구 최소 줌에서 필드 전체가 보인다
7. 컬링 최소 줌에서 던지는 곳과 타겟 라인이 동시에 보인다
8. Gowun Dodum 의 얇은 획이 밝은 배경 위에서 읽힌다

## 화면별

### 인게임 HUD

측정한 것: 축구 최소 줌 프레임에서 UI 가 차지하는 면적.

| 요소 | 지금 | §11 판정 |
|---|---|---|
| 스코어 | 벡터 숫자 + 캡션. **판 없음** | 유지 — PHASE 0 에서 이미 §8.1 |
| 턴 플레이트 | 흰 판 + 색 알약 + `PLAYER 1` | **판 제거.** 색 알약과 글자만 남긴다 |
| 클럭 바 | 채워지는 막대 | **짧아지는 선으로.** §8.1 이 명시 |
| 나가기 | 아이콘 + 판 | **판 제거.** 아이콘만, 히트는 `CTA.hitPad*` |
| 리센터 | 아이콘 + 판 | 같음. `atDefaultView()` 로 흐려지는 로직은 유지 |
| 뒤집기 | 아이콘 + 판 | 같음 |
| 카드 손패 | 카드 면 + 뒷면 | 유지. 면은 PHASE 6 에서 종이로 |

**턴 플레이트의 판이 제거 대상인 이유**가 이 감사의 핵심 사례다. 판은
"PLAYER 1" 을 읽히게 하려고 있는데, 그 글자가 놓이는 곳은 목재이거나 잔디이고
둘 다 `ui.text` 가 5:1 을 넘는다 — 판이 없어도 읽힌다. 판이 실제로 하는 일은
**필드를 가리는 것**이고, 축구 최소 줌 프레임에서 그 판은 필드의 왼쪽 아래
모서리를 덮는다. §11 의 "필드가 화면을 지배한다" 와 정면으로 부딪친다.

색 알약은 남는다. 그것은 장식이 아니라 침해 불가 1번의 절반이다 — 지금 누구
차례인지를 **색으로** 말하는 유일한 것이고, 글자는 그것을 두 번 말한다.

**스코어 위치**는 축소가 아니라 이동이다. 실측 스크린샷에서 축구의 스코어가
골 에어리어 선 위에 겹친다. 필드 밖으로 — §11 의 "주변에 조용히" 는 위치에
대한 말이기도 하다.

### 메뉴 (홈)

| 요소 | 지금 | 판정 |
|---|---|---|
| 병 | 떠 있음, 라벨에 이름 | 유지 |
| 제목판 | 둥근 흰 판 + `한여름 알까기` + `메인 메뉴` | **축소** |
| 모드 셋 | 글자 + 밑줄 | **PLAY 로 묶음** (사용자 결정) |
| 설정 · 마크 | 아이콘 + 판 | **판 제거** |

제목판은 화면에서 가장 큰 흰 사각형이고 §11 의 "두꺼운 패널" 이다. 그리고
`한여름 알까기` 는 **텍스트**로 그려져 있다 — §4.4 가 제목을 벡터로 그리라고
했고 `lettering.drawTitle` 이 있는데 여기가 아직 안 쓰고 있다. 판을 없애고
레터링으로 바꾸면 두 조항이 한 번에 해결된다. `메인 메뉴` 라는 부제는 제거 —
메인 메뉴에 있다는 사실은 화면이 이미 말한다.

홈 구조는 사용자가 **PLAY 하나로 묶기**로 답했다. 그러면 홈은 세 줄이 된다:
`PLAY` · `COLLECTION` · `SETTINGS`. 모드 셋은 PLAY 안으로.

### 설정

일곱 줄. 전부 §11 의 "최소 정보" 안이고 제거할 것이 없다. 하나만:

**볼륨 칩 열 개**는 값 하나를 열 개의 물체로 말한다. 지금 그 줄은 `마스터 볼륨
70%` 라는 **숫자**와 칩 열 개를 **동시에** 보여주므로 같은 것을 두 번 말하고
있다 — v2 감사의 2번 기준("두 표시가 같은 것을 말하는가")에 걸린다. 칩을 얇은
선 하나와 그 위의 표식 하나로 바꾼다. 그래픽 다섯은 남긴다: 다섯은 셀 수 있고
티어는 **이름**이 있는 이산값이라 눈금이 정보다.

서버 주소는 이미 `?debug=1` 뒤에 있다 (v2 감사에서 처리됨).

### 상대 선택 / 온라인

상대 선택은 뚜껑 둘 + 세 줄 + 푸터 둘. 뚜껑 둘은 유지 — 그것이 이 화면에서
고르는 것이고, §9 의 연쇄에서 뚜껑이 말이 되는 자리다. 캡션이 이제
`SUMMER PORCH` 를 말한다 (§7.4).

온라인은 상태 한 줄 + 세 경로 + 뒤로. 세 경로가 각각 다른 일을 하므로 유지.

### 마크 화면 / 편집기

편집기가 이 프로젝트에서 가장 요소가 많은 화면이다 — 스와치 24, 도구 7, 상단 2,
푸터 2, 턴테이블 1. **거의 전부 유지한다.** §11 은 게임 화면의 규칙이고, 이것은
그리기 도구다. 도구가 적은 그리기 도구는 조용한 것이 아니라 부족한 것이다.

축소 하나: 도구 열의 아이콘마다 붙은 **판**을 없앤다. 일곱 개의 둥근 사각형이
세로로 쌓인 것이 §24 가 부르는 "generic rounded UI cards" 에 가장 가까운 그림이고,
아이콘 자체가 이미 서로 다른 모양이라 판이 구분에 기여하지 않는다.

스와치 24 는 유지 — 팔레트 주석이 그 개수와 순서를 **레이아웃**이라고 못박았고,
플레이어의 그리기 도구가 게임의 두 색으로 제한되면 모든 마크가 게임이 그린 것처럼
보인다.

### 승리 화면

한 줄(`1P 승리`) + 스코어 + 버튼 둘 + 레터박스. 축소 하나: 승리 줄이 지금
`TYPE.body` 를 판 높이에서 키운 것이다. PHASE 5 에서 **판을 없애고** 필드 위에
직접 놓는다 — 인게임 스코어와 같은 처리이고, 같은 이유로.

레터링으로 그리지 **않는** 이유는 `hudTextures` 에 적어 두었다: 내용을 우리가
정하지 않는다. `1P 승리` 에 라틴 대문자가 있고 모드가 `outcomeFor` 로 자기 문장을
넣을 수 있으며, 레터링에 없는 글자는 빈 상자로 나온다.

### 인트로 / 레터박스

**유지.** §7.1 이 폐기한 것은 **전환**으로서의 레터박스이고, 그 자리는 뚜껑이
가져갔다 (PHASE 2). 경기 자신의 시작과 끝을 액자에 넣는 것은 전환이 아니라
연출이고, 바는 `bg.skyTop` 코발트이지 검정이 아니라 §24 의 "dark interfaces" 에
걸리지 않는다.

## §14 침해 불가 여덟 항목 — 실측

| # | 항목 | 측정 | 판정 |
|---|---|---|---|
| 1 | 1P/2P 뚜껑 | 절대 휘도차 0.174 (요구 0.15), 색상 12° 대 220° | 통과 |
| 2 | 아웃 라인 | `cobaltInk` 대 목재 5.31:1 (요구 3.0) | 통과 |
| 3 | 오차 콘 | 가장자리 대 목재 1.86 · 잔디 2.21 · 테이블 1.86 | **조건부** — 아래 |
| 4 | 컬링 마크 | `targetDark` 대 테이블 5.31:1, 대 `targetLight` 8.10:1 | 통과 |
| 5 | 카드 세 상태 | `skinFor` 의 idle/disabled/dimmed 가 잉크와 선 굵기 둘 다 다름 | 통과 |
| 6 | 축구 최소 줌 | 실측 스크린샷에서 필드 전체 + 양 골 | 통과 |
| 7 | 컬링 최소 줌 | 실측 스크린샷에서 던지는 곳과 체커 라인 동시 | 통과 |
| 8 | 얇은 획의 가독성 | `micro` 10px 는 게임에서 12.5~19.7 CSS px 로 그려진다 | 통과 |

3번만 조건부다. 팔레트 값은 통과하지만 §5.2 가 지정한 알파(채움 0.10~0.14,
가장자리 0.35)를 곱한 뒤의 실제 화면 대비는 안 쟀다.

**PHASE 7 에서도 못 쟀다.** 합성 포인터 이벤트로 조준을 흉내 내는 것이 안 된다 —
`PointerRouter` 까지 닿지 않아서 오버레이가 그려지지 않고, 그 상태로 잰 값들은
전부 판의 나뭇결이었다. `overlay.update` 를 직접 부르면 유니폼과 지오메트리는
바뀌지만 루프가 다음 프레임에 `setVisible(false)` 로 덮는다.

산술로는 통과한다: `whiteCool` 선형 휘도 0.948 을 알파 0.12 로 목재(0.38) 위에
올리면 0.448 이고, 경계 양쪽의 대비는 1.14:1 이다. 사람 눈이 **경계**에서 밝기
차이를 잡아내는 문턱은 1~2% 근처이므로 14% 는 그보다 한참 위다. 면 전체의 대비를
1.5:1 로 올리려면 알파가 0.38 이어야 하고, 그건 판을 덮는 흰 쐐기다 — §11 의
"필드가 화면을 지배한다" 와 정면으로 부딪친다.

**남은 검증은 손으로 하는 플레이 한 판이다.** 그 전까지 이 항목은 조건부다.

## 이 감사가 찾은 결함 (감사 중 수정)

1. **`markIcons.iconTexture` 가 죽어 있었다.** PHASE 0 의 `gelButton → plate`
   개명이 같은 이름의 **불리언 파라미터**와 충돌해서, `if (plate) plate(ctx, …)`
   가 "plate is not a function" 으로 던졌다. 빌드는 통과한다 — 둘 다 스코프
   안의 유효한 식별자다. 내 마크 화면을 여는 순간 죽었고, 화면을 하나씩 열어
   보는 이 감사가 아니었으면 PHASE 5 까지 안 보였다.
   같은 그림자가 `messageTexture` 와 `titleTexture` 에도 있었다 — 그쪽은 우연히
   `panel` 을 불러서 살아 있었다. 셋 다 `withPlate` 로 바꿨다.

2. **RETREAT 라벨의 `◀` 중복** (PHASE 2 에서 수정). `roleButton` 이 화살표를
   그리는데 라벨에도 글리프가 있었다.

## 승인이 필요한 결정

1. **위 표의 제거 3 · 축소 6.** 전부 §14 를 침해하지 않는다.
2. **홈의 COLLECTION.** 사용자가 "별도 화면을 새로 만든다" 로 답했으나,
   **수집 대상이 되는 시스템이 아직 없다.** 마크는 플레이어가 그리는 것이지
   모으는 것이 아니다. 무엇을 모으는가를 정하지 않으면 이 화면은 빈 격자다 —
   PHASE 5 에서 홈에 자리만 만들고 화면은 그 답을 받은 뒤에 만들 것을 제안한다.
3. **인트로 레터박스 유지.** 위 근거로 유지를 제안하되, §7.1 을 문자 그대로
   읽으면 이것도 폐기 대상이다. 폐기하면 경기의 시작과 끝에서 액자가 사라지고
   그 자리를 대신할 것을 PHASE 5 에서 새로 만들어야 한다.
